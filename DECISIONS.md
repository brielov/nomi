# Decisions

One dated paragraph per decision that would be expensive to reverse. If a decision can be a test, it is a test instead.

**2026-10-07: test support is a dev-only crate.** Parity ratchets are checked from each crate's own tests, so the ratchet code must be shared between crates. It lives in `nomi-testkit`, which any crate may take as a dev-dependency and none as a normal one; `xtask ci` enforces both. The alternative, running every suite through `xtask`, would put compiler APIs behind a process boundary for no gain.

**2026-10-07: corpus claims are per Compat.** Upstream accepts an application only when its `elm-version` equals the compiler's version, and a package only when its range admits it; the pinned apps all say 0.19.1 and 14 corpus packages exclude 0.19.3. So exit criteria that say "every corpus package/app/project" (M5, 6.7, 7.4, 7.5, 8.10) now mean every one the Compat accepts, with the rejected ones kept as expected-failure cases whose diagnostics must match (plan 1.15a). Oracle sandboxes rewrite app `elm-version` to the Compat under test. The alternative, pinning only projects every Compat accepts, would drop the apps from 0.19.2 and 0.19.3 entirely.

**2026-10-07: elm columns count code points, and the release decides the rest.** Probes with `é` and `😀` before a syntax error put the error at the same column in 0.19.1, 0.19.2 and 0.19.3, which counts code points, not UTF-8 bytes or UTF-16 units. A CR doesn't advance the column. 0.19.2 prints rows and columns from 0 where the others start at 1. 0.19.1 keeps rows and columns in 16 bits, so its parser sees a token at 1-based column 65,536 at column 0 and rejects three corpus modules with lines that long; the later releases accept them. So the validation pass takes a `Compat` along with the project kind, and regions will too (plan 4.4). The alternative, one column model for every release, would misjudge those modules for one release or the others.

**2026-10-07: modules parse in two layouts.** elm wants every continuation token right of its construct; elm-format checks indentation only before arguments and when aligning blocks, so it takes a declaration body, a closing parenthesis or an operator at column 0. One grammar serves both: `Layout::Strict` parses as elm does, which also recovers well from broken code, and when that fails `Layout::Loose` parses again, demanding indentation only where elm-format does. A clean loose parse wins and records each unindented token it consumed, which validation reports for elm. An error file costs two parses. The alternatives were a separate elm-format grammar, which would double every later syntax change, or one loose parse, whose recovery from a missing `)` or `=` swallows the next declaration.

**2026-10-07: doc comments use a Cheapskate port.** elm-format parses doc comments with its own fork of Cheapskate, which disagrees with CommonMark on lists, code block ends, `@docs` lines and more, and what it parses decides both the printed comment and which code blocks are Elm. So `format/src/markdown/` ports the fork and upstream's Markdown printer, quirks included, and lowering parses each Elm code block into the formatter tree as declarations, then expressions, then a module, as upstream tries them. The alternative, pulldown-cmark, would need a correction layer for every divergence, and the corpus has hundreds of doc comments that would find them.

**2026-10-07: an empty non-Elm code block prints as a blank line.** elm-format crashes on a code block with a language other than `elm` and no text (`Data.Text.last: empty input`). nomi prints the fence around one empty line, as it does for any code without a final newline. The `nomi/code_fences` fixtures that elm-format crashes on cover it. The alternative, rejecting every module with such a block, would refuse modules elm accepts.

**2026-10-07: invariant breaks follow upstream until decided.** elm-format 0.8.8 itself breaks the formatter's invariants: it drops comments in the module header, can leave an exposing list unparseable, moves some comments and doc-comment Markdown on a second run (48 corpus modules), prints `\x` escapes as other code points, prints `{-- }…-}` as a comment that ends at `{--}`, can unbalance a comment nested in a doc comment, which then swallows or exposes code, reflows `(f x) y` and `[a..b] y` spanning lines differently on a second run, prints an Elm 0.18 infix declaration that a comment spreads over lines as a request to report it, exposes both a type alias and a type of one name in a module without a header, as `Y(..), Y`, where a second run exposes `Y(..)` alone, and prints a float too large for a double as `Infinity`, a name Elm doesn't define. Each nomi break on the fixtures, the corpus and the fuzzer's findings was checked to be upstream's, byte for byte, and is listed in an `invariants.tsv` beside the parity tables; property tests and the fuzzer allow only these classes (`upstream_breaks`). Parity stays the default, and 2.15 turns each class into a fixed deviation or keeps it. The alternative, fixing them during 2.14, would mix deviations into the parity work before the corpus says which ones matter.

**2026-10-08: comments the docs move stay inside the exposing list.** When `@docs` reorders the exposing list, elm-format gathers the comments of the items it moved after them, joined like an item, so a one-line list ends `(x, y, {- c -})`, which doesn't parse. nomi prints them after a space, `(x, y {- c -})`, which a second run reads back the same; a list spanning lines already stacks them before `)` and stays as upstream. The `nomi/export_comments` cases under `format_fixtures/deviations/` cover it. With this, formatting a module with comments must keep it parseable, which the invariant checks now hold it to. The alternative, attaching the comments to the last item, would also move them in the lists that span lines, where upstream's output is fine.

**2026-10-08: a `{--` comment keeps the space that keeps it one comment.** elm-format drops the spaces after `{--` and before `-}`, so `{-- } a -}` prints as `{--} a-}`, a comment that ends at `{--}` and leaves the rest as code, and `{-- a { -}` as `{--a {-}`, whose `{-` opens a comment that never closes. nomi keeps one space before a leading `}` and after a trailing `{`, and spells every other `{--` comment as upstream does. The `nomi/trick_blocks` fixture covers it. The alternative, keeping all of the comment's spaces, would change the many `{--…-}` comments upstream prints fine.

**2026-10-08: a float too large for a double prints as `1.0e309`.** elm-format reads a float literal into a double and prints the overflow as `Infinity`, a name Elm doesn't define, so `1e999` formats to code that no longer compiles. nomi prints an infinite magnitude as the least power of ten that reads back as infinite: `1.0e309` where upstream would use an exponent and `1` with 309 zeros and `.0` where it would write the digits out, with the sign in front as upstream. Elm keeps a float literal's text for JavaScript, which reads both as `Infinity`, so the meaning holds and a second run prints the same. The `nomi/large_floats` fixture covers it. The alternative, keeping the literal as written, would need the formatter's tree to carry source text for every float to serve a case that only overflowing literals reach.

**2026-10-08: a doc comment whose reprint would end elsewhere stays as written.** elm-format reprints a doc comment from its Markdown, which can undo the nesting of a comment inside: a code block's info string keeps only its first word, so ```` ```elm {- a ```` loses the `{-` that a later `-}` closes, and the reprinted comment ends early or swallows the code after it. nomi lexes the reprinted comment and, unless it is one doc comment, prints the comment as written, without trailing whitespace. The `nomi/doc_comment_nesting` fixture covers it. The alternative, repairing the Markdown, would mean guessing which of the comment's parts the author meant as code; keeping it as written is what they had and stays parseable.

**2026-10-08: the remaining invariant breaks stay upstream's.** 2.15 deviates where elm-format's output of code Elm accepts doesn't parse or reads differently: comments the docs move into a one-line exposing list, `{--` comments that end early or never close, floats too large for a double, and doc comments whose reprint ends elsewhere. The other breaks stay as elm-format makes them. Comments it drops from the module header, comments and doc-comment Markdown that move on a second run, and `(f x) y` or `[a..b] y` reflowing on a second run all leave code that compiles to the same program, and changing them would move nomi's first run away from elm-format's on all 48 corpus modules they reach. `\x` escapes, Elm 0.18 infix declarations printed as a request to report them, and a module without a header exposing `Y(..), Y` arise only from code Elm 0.19 rejects, so there is no meaning to keep. `upstream_breaks` lists these five classes, and the `invariants.tsv` tables the modules that reach them. The alternative, making nomi idempotent everywhere, would trade parity on modules people format today for a second run they rarely make.

**2026-10-08: a negated negation keeps its parentheses.** elm-format drops the parentheses around a negation's operand when the operand needs none, so `-(-x)` prints as `--x`, which starts a comment that swallows the rest of the line. nomi keeps the parentheses when the operand prints starting with `-`. A negated zero stays upstream's: `-(0)` prints as `-0`, which a second run reads as `0`, the same number. The fuzzer found both through `1 -(1e2)`, which prints as `1 -1.0e2`, one negative literal where the source had a negation; the token check now reads both alike.

**2026-10-08: elm-format's command line deviates where its output depends on chance.** Invoked as `elm-format`, nomi parses elm-format 0.8.8's arguments as its optparse-applicative parser does and repeats its prompts, messages, `--validate` JSON and exit codes byte for byte; `crates/cli/tests/elm_format/` holds the cases and elm-format's transcripts. It differs in five ways. A directory's modules come in the order of their names, where elm-format takes the order the disk lists them in, and the modules it formats at once report in the order they were named, where elm-format's threads interleave. A file that isn't UTF-8 is a syntax error at its first bad byte and stays as it was, where elm-format reads replacement characters and can write them back. Files are replaced in one step, and an I/O failure is reported for its file while the others go on, where elm-format writes in place and dies at the first failure. `--elm-version` 0.17 and 0.18, and a project elm-format would take for 0.18, exit with one line saying nomi formats 0.19 only (`deviations/` covers them). The internal `--json` and `--from-json` flags are unknown options. Syntax errors are reported where elm-format's parser stops, from a port of it (the entry on elm-format's syntax error positions). The alternative, reproducing disk and thread order, would make every run's output depend on the machine, which no caller can rely on today either.

**2026-10-08: the 0.19.1 solver oracle is built from 0.19.2's sources.** The solver oracle compiles upstream's `Deps/Solver.hs` with the GHC 9.14.1 that D3 pins. 0.19.1's sources don't compile with it (`Data/Utf8.hs` mixes `Word#` and `Word8#`), and GHC 9.8, which D3 allowed as the fallback, is past GHC 9.2's split of the two, so it fails the same way. So 0.19.1's oracle is 0.19.2's sources with `Paths_elm` saying 0.19.1, which sets `V.compiler`. Between the two tags, `Deps/Solver.hs` differs only in how decoding threads through IO, and `Elm/Outline.hs` and `Elm/Constraint.hs` only in parser plumbing, so the search and the `elm-version` checks are 0.19.1's. The alternative, an older GHC with an older package set, would put a second toolchain on every machine that records snapshots, for code that doesn't differ.

**2026-10-08: upstream's search selects, PubGrub explains.** nomi must pick the versions upstream's `Deps/Solver.hs` picks: pending packages in name order, versions newest first, depth first, the first solution found. PubGrub with name priority and newest-first versions agrees with that on every 3.6 scenario, but not in general: over 200,000 random registries it picked differently 24 times when dependencies could form cycles and 79 times when each package depended only on earlier names, because conflict learning backjumps past choices the plain search would revisit. Scenario `pubgrub-differs` is one of those registries, and upstream answers as the port does. So `registry::solver` is a port of upstream's search, and `solver::explain` runs PubGrub over the same releases only once that search has found nothing, to say why. The two can't disagree on whether a solution exists, which a test checks. The alternatives were PubGrub alone, which would change what `install` writes, or the port alone, which can only say "no solution".

**2026-10-08: `install` changes elm.json and downloads, but doesn't build.** Invoked as `elm`, `init` and `install` repeat elm's prompts, plans, `elm.json` edits and reports byte for byte; `crates/cli/tests/elm/` holds the cases and elm's transcripts. Upstream's `install` goes on to build every dependency and reports a build failure as an install failure; nomi checks the new dependencies, downloads them into its store, and leaves building to the builds that need it (milestone 4), so a package that downloads but doesn't compile installs fine. When that check fails nomi writes back the original bytes of `elm.json`, where upstream re-encodes the outline it read, which can change the file's spacing. INSTALL WHAT? names nomi's package store where elm names `ELM_HOME`, so its hint wraps differently, and an engine test covers it instead of the transcript. HTTP failures say less than upstream's, since nomi's client keeps no response headers or bodies. nomi takes no lock on the project, as elm does around `install`, until builds share a project (milestone 4). The alternative, building during `install`, would need milestone 4's build graph inside a step of milestone 3.

**2026-10-08: `rm` keeps the versions it has.** Upstream has no `remove`, so `nomi rm` (alias `remove`) is nomi's own, with messages in `install`'s style. It doesn't call the solver: an application keeps its direct dependencies but the one removed, and its indirect and test dependencies become what the remaining ones reach through the releases already in `elm.json`, at those versions. So `rm` never upgrades or downgrades anything, never needs a solution that might not exist, and undoes an `add` that only inserted packages, byte for byte, which `removing_undoes_adding` checks over the solver scenarios and a CLI test checks through `add` and `rm`. A package loses the one constraint. An indirect dependency can't be removed on its own; the report names what needs it. The alternative, re-solving for the remaining dependencies, would pick the newest versions and so turn every removal into an upgrade the user didn't ask for.

**2026-10-08: `update` stays within major versions.** Upstream has no `update`, `outdated` or `tree`, so they are nomi's own. `nomi update` lets each of an application's direct and test dependencies move up to its next major version, which keeps its API, and re-solves what they need with upstream's search, so it picks what `install` would. `update <package>` frees only that package and the dependencies that need it; the rest are held exactly, and if that fails only the other direct ones are. `updating_stays_within_majors` checks over the solver scenarios that no direct dependency moves back or across a major version, that elm accepts the result, that a second update changes nothing, and that one package's update moves only what needs it. A package's elm.json holds ranges, which every build already resolves to the newest releases they allow, so `update` there writes nothing. `outdated` reads the index only: an application's direct dependencies with newer releases, and a package's with releases past its ranges. The alternative, letting `update` cross major versions, would rewrite code's dependencies under it; that belongs in a separate, explicit command if anyone asks for one.

**2026-10-08: snapshots freeze the editor's text, not the disk.** A `Snapshot` of the `Vfs` shares the overlays as they were at its revision, so an edit never changes text under a reader. It reads the disk when asked instead of copying it: copying every file a build might read would cost what reading it does, and the disk can change without nomi knowing anyway. Instead, every write nomi makes, and every change a watcher reports through `disk_changed`, makes a new revision, which marks older snapshots stale so their work stops between phases and starts again (architecture §6). A `FileId` comes from the path with every symbolic link resolved; of a file not on disk yet, an editor's unsaved buffer, the longest part that exists is resolved and the rest taken lexically. On macOS this also folds a path's case to the disk's. Ids are never reused, so a path keeps its id for the life of the `Vfs`.

**2026-10-08: the module graph finds upstream's first cycle, except where 0.19.3 crashes.** `engine::graph` crawls as `Build.hs` does and orders modules per release, by bytes in 0.19.1 and 0.19.2 and by length then bytes in 0.19.3, because that order chooses the cycle reported when there are several. 0.19.1 and 0.19.2 report the whole first component; 0.19.3 reports the shortest cycle through its first module. Default imports are part of the graph, as upstream crawls them; leaving them out changes which component comes first. A model of this was compared with all three elm releases over 100 random graphs, with no differences. There is one deviation. When the first module of 0.19.3's component imports itself, `withMinimalCycle` reads outside its array, and elm crashes or hangs; nomi reports that module alone, as the older releases do. A module that isn't UTF-8 is unreadable here, where upstream parses its bytes as they are; 4.11 words the report. The alternative, Tarjan's algorithm or any order of nomi's own, would report another cycle than elm's on the same project.

**2026-10-08: a damaged artifact is a miss, and the cache trims like Go's.** `engine::artifacts` keeps what builds make in one per-user directory, each entry filed under a SHA-256 of everything its build read: the kind, nomi's version, and the named, length-prefixed parts the caller adds (source, `Compat`, imports' interface hashes, package). An entry repeats its key and its payload's length and hash, as the first attempt's did, and any entry that doesn't check out is read as a miss and replaced by the next build. The first attempt failed the build instead, which turns a disk fault or a killed write into an error the user must clear by hand, for a cache whose whole contract is that it can be rebuilt. Trimming follows `GOCACHE`: reading an entry refreshes its time at most hourly, and at most daily the entries unused for five days are removed, so the cache needs no size setting and no command to clean it. The scheduler runs the module DAG with a counter per module rather than in waves, so a slow module holds up only what imports it; the outcomes come back in the modules' order whatever order they ran in.

**2026-10-08: snippets show positions as each release keeps them.** 0.19.1 keeps rows and columns from 1 in 16 bits, and 0.19.2 and 0.19.3 from 0 in 32. Most snippets hide this, since `viewLineNumber` adds the 1 back, but `Code.toPair` on one row prints the row as kept, so from 0.19.2 on the first line of a file shows as `0|`. nomi repeats it, and wraps 0.19.1's rows and columns past 65,535 as upstream does. `--report=json` regions count from 1 in 0.19.1, from 0 in 0.19.2, and from 1 again in 0.19.3, which adds 1 for editors. Documents name the code they show by byte range, and `code::expand` puts in the lines for one release just before layout, so a diagnostic holds no source text and renders for any release. Text and JSON match elm's output in all three releases for one-row and two-row pairs, a region over rows, and a tab in the source. Where upstream fails, on a snippet with no lines or a pair on a row past the end, nomi shows an empty line. The alternative, rendering snippets when a phase reports them, would tie every diagnostic to one release and to its file's text.

**2026-10-08: elm.json reports are upstream's, except where upstream hangs or dies.** `nomi_project::report` ports `Reporting/Error/Json.hs` and the outline half of `Reporting/Exit.hs`, and `nomi_registry::report` the details and package halves, so every command that reads a project reports a broken `elm.json`, a hand-edited dependency set or a corrupt download as elm does. `cargo xtask oracle outline` records each release's `--report=json` for 41 broken fixtures, and `tests/reports.rs` compares nomi's 472 reports with them byte for byte; transcripts cover the reports about more than the file. nomi deviates in five places. `expectationToReport` defines the region of a value on one row as itself, so upstream hangs after the first paragraph; nomi underlines the value, and a value over rows shows its first position, as upstream does. 0.19.1 counts the rows before a parse error in 16 bits, so an error on the first row starts at row 65,535 and dies; nomi starts at the first row, as later releases do. 0.19.1 also dies on a string byte that can't start UTF-8, which nomi reports as UNEXPECTED ENCODING, as later releases do. 0.19.1's details reports suggest "the dependency management tool in elm reactor" only when invoked as `elm`, since nomi has no reactor. A store that can't be read or written gets a report of nomi's own, since upstream's store has no such failure. Missing source directories are checked on disk, not in the `Vfs`, which tracks files only, and redundant ones by their canonical paths, compared as strings so the pair reported is upstream's. The alternative, repeating upstream's hangs and crashes, would leave a user with no report at all.

**2026-10-08: elm's syntax errors come from a port of its parser.** elm's title and region for a syntax error depend on where its backtracking parser gives up and on every context it unwinds through: which alternative of a `oneOf` consumed input, where each `inContext` started, and whether `Space.chomp` had run, which counts as consuming input even when it eats nothing. nomi's grammar recovers and resynchronizes, and its first error agrees with elm's position on about two thirds of the mutation suite. So `nomi_syntax::elm` ports `Parse/*.hs` and the error types of `Reporting/Error/Syntax.hs`, one parser for every release with 0.19.1's 16-bit, 1-based rows and columns behind its `Cursor`, and runs it only on a module the grammar rejects. It builds no tree and serves no other caller; the mutation suite holds it to rejecting exactly what each release rejects, so the two can't drift unseen. The alternative, teaching the recovering grammar to record upstream's constructors, would mean reproducing a backtracking parser's failure points in one that doesn't backtrack, case by case, across 29,511 rejected mutations.

**2026-10-08: elm-format's syntax error positions come from a port of its parser.** elm-format reports an unparsable module at the row and column where its Parsec-style parser's last error continuation ran, which depends on every `try`, `<|>` and `commitIf` it went through, on its own column counting (a tab to the next multiple of eight in `satisfy`, one column a character in the number and string primitives), and on 16-bit rows and columns that wrap. nomi's first error is at the same place on 64% of the mutation suite's rejected cases. So `nomi_syntax::elm_format` ports elm-format 0.8.8's `Parse/*.hs` for 0.19 syntax, over its `ParsecAdapter` semantics, and `format_text` reports its position when nomi's grammar rejects a module, falling back to nomi's own where the port accepts or crashes. Like the port of elm's parser, it builds no tree, returning only what upstream's control flow reads back: whether a pattern is a variable, and whether a parenthesized pattern had comments. The mutation suite holds it exact on all 27,814 rejected cases. Where elm-format itself crashes (`satisfy` on U+FFFE or U+FFFF, `many` over a parser that accepts nothing) the port says so, and nomi reports its own position rather than crash. The alternative, recording elm-format's position in nomi's recovering grammar, would mean reproducing a second backtracking parser's failure points in one that doesn't backtrack.
